> 3. Execute the phases in section 7 in order. After each phase run `lint`, `typecheck`, `test` and `build`, fix everything, then print a short summary and continue.
> 4. If `mini-cafe-spec.json` exists in the repo or was provided, treat it as the visual reference. Values in `src/config/*` always win over it.

## 1. Goal

A mobile-first, RTL, Persian web app for a small mobile cafe. A customer scans a QR code, sees the menu, picks items, sees a live total, then pays online (gateway link) or by card-to-card transfer.

**The main design requirement is easy change later.** Renaming the cafe, changing prices, colors, payment info or texts must each be a one-file edit, with no hunting through components.

## 2. Stack decisions

| Area | Decision | Why |
|---|---|---|
| Framework | Next.js (latest stable), App Router, TypeScript `strict` | Requested; good DX |
| Rendering | **Static export** (`output: "export"`) | No server needed. Deploys to cPanel, Netlify, Vercel or any static host |
| Styling | Tailwind CSS v4 + CSS variables as design tokens | Theme changes in one place |
| State | `zustand` with `persist` on **sessionStorage** | Tiny; cart survives the redirect to the payment gateway and back |
| Font | Vazirmatn, self-hosted via `next/font/local` (woff2 from the `vazirmatn` npm package) | No external request at runtime |
| Tests | Vitest, unit tests for pure logic only | Money and cart math must never break |
| Package manager | pnpm (npm is fine if pnpm is unavailable) | |
| Not in v1 | Backend, database, auth, CMS, analytics | Keep it simple |

`next.config.ts`:

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "export",
  images: { unoptimized: true }, // required for static export
  basePath: process.env.NEXT_PUBLIC_BASE_PATH ?? "",
  trailingSlash: true,
};

export default nextConfig;
```

## 3. Architecture principles

1. **Single source of truth.** Names, prices, colors, card number, gateway link and all UI strings live in `src/config` and `src/content`. Components never hardcode them.
2. **Feature folders.** `features/menu`, `features/cart`, `features/payment`. A feature can be changed or deleted without touching the others.
3. **Pure logic is separate and tested.** Money formatting and cart totals live in plain functions that take data as arguments (no hidden imports of config), so they are trivial to unit test.
4. **Payment is behind an interface.** Adding or swapping a payment method means adding one file and one registry line.
5. **Money is an integer in toman.** No floats. Formatting happens only in `lib/money.ts`.
6. **Theme is tokens.** `site.theme` becomes CSS variables on `<html>`; Tailwind classes use those variables. No raw hex values in components.
7. **UI primitives are dumb.** `components/ui/*` take props only and know nothing about the cafe.

`layout.tsx` converts `site.theme` into CSS variables (`--bg`, `--card`, `--border`, `--accent`, `--text`, `--muted`, `--on-accent`) on `<html style={...}>`. `globals.css` maps them in Tailwind `@theme` so classes like `bg-bg`, `bg-card`, `text-accent`, `border-border` work.

### 5.2 `src/features/menu/types.ts` and `src/config/menu.ts`

```ts
export type MenuItem = {
  id: string;            // stable, never reused (cart is keyed by it)
  name: string;
  price: number;         // integer, toman
  icon?: string;         // emoji fallback
  image?: string;        // e.g. "/images/menu/tea.webp" (optional, added later)
  description?: string;
  category?: string;     // reserved for future tabs
  available?: boolean;   // default true; false = shown as sold out, cannot be added
  badge?: string;        // e.g. "ویژه"
};
```

```ts
import type { MenuItem } from "@/features/menu/types";

export const menu: MenuItem[] = [
  { id: "tea", name: "چای نبات", price: 35000, icon: "🍵" },
  { id: "nes", name: "نسکافه", price: 70000, icon: "☕" },
  { id: "ali", name: "علی کافه", price: 80000, icon: "☕" },
  { id: "cap", name: "کاپوچینو ترابیکا", price: 90000, icon: "🥤" },

```

`MenuCard` shows `image` if present, otherwise `icon`. Adding photos later must require **no component change**, only editing `menu.ts` and dropping files in `public/images/menu/`.

### 5.4 `src/features/payment/types.ts`

```ts
import type { ComponentType } from "react";
import type { CartLine } from "@/features/cart/selectors";

export type PaymentMethodId = "gatewayLink" | "cardToCard";

export type PaymentProps = { total: number; lines: CartLine[] };

export type PaymentMethod = {
  id: PaymentMethodId;
  Component: ComponentType<PaymentProps>;
};
```

`registry.ts` exports `Record<PaymentMethodId, PaymentMethod>`. `PaymentSection` renders `payment.methods` in order. **Adding a method = new provider file + registry entry + id in the union + id in config.**

### 5.5 Cart

```ts
// store.ts: only quantities, nothing derived
type CartState = {
  quantities: Record<string, number>;
  add: (id: string) => void;
  remove: (id: string) => void; // never below 0, delete key at 0
  clear: () => void;
};
```

```ts
// selectors.ts (pure)
export type CartLine = { item: MenuItem; qty: number; subtotal: number };
export function buildLines(q: Record<string, number>, menu: MenuItem[]): CartLine[];
export function getTotal(lines: CartLine[]): number;
```

`buildLines` must ignore ids that are not in `menu` or are `available === false` (stale persisted carts after a menu change).

### 5.6 `src/lib/money.ts`

```ts
export const formatToman = (n: number) => `${n.toLocaleString("fa-IR")} تومان`;
export const formatThousandToman = (n: number) =>
  n % 1000 === 0 ? `${(n / 1000).toLocaleString("fa-IR")} هزار تومان` : formatToman(n);
export const tomanToRial = (n: number) => n * 10; // for gateways that need rial
```

## 6. UI behavior (reference)

- Page: RTL, max width 480px, centered, works from 360px, no horizontal scroll, respects safe-area insets, `viewport-fit=cover`. Decorative yellow circle clipped at the top-left corner.
- **Header:** inline SVG yellow cup, `site.name` (large, accent color), `site.tagline` (small, letter-spaced, LTR), short accent divider.
- **Menu:** 2-column grid. Each card: icon or image, name, short accent divider, price pill (`formatThousandToman`, accent background, `onAccent` text), quantity stepper (plus / count / minus).
- **Cart panel:** title, one row per line (`name × qty` and subtotal), total bar (accent background, `aria-live="polite"`).
- **Payment section** (below the total, buttons disabled when total is 0):
  - Gateway button: copies the total (digits only) then opens `gatewayLink.url` in a new tab. Empty url shows the `gatewayMissing` toast.
  - Card-to-card: card number formatted `6219 8618 0433 2251` (LTR, large, accent color), buttons to copy the card number and the amount.
- **Footer:** `site.footerText`, italic, accent color.
- **Accessibility:** all steppers have Persian `aria-label`s, tap targets at least 40px, visible `:focus-visible` ring, text contrast on navy and yellow checked.
- Clipboard calls go through `lib/clipboard.ts` (try/catch, returns boolean). Toast auto-hides after 2.5s.

## 7. Phases

### Phase 1: Scaffold and tooling
- Create the Next.js app (App Router, TypeScript, Tailwind, ESLint, `src/` directory, import alias `@/*`).
- Apply `next.config.ts` from section 2. Add `.env.example`.
- Add Vitest with a `test` script. Add a `typecheck` script (`tsc --noEmit`).
- Install `vazirmatn`, copy the variable woff2 into `src/assets/fonts/` (verify the exact file name inside `node_modules/vazirmatn`), load it with `next/font/local`.
- **Done when:** `pnpm dev` shows an empty RTL page in Vazirmatn; `lint`, `typecheck`, `test`, `build` all pass and `build` produces `out/`.

### Phase 2: Config, content, utilities
- Create `config/site.ts`, `config/menu.ts`, `config/payment.ts`, `content/fa.ts`, `lib/money.ts`, `lib/clipboard.ts`, `features/menu/types.ts`.
- Wire theme tokens: `site.theme` to CSS variables in `layout.tsx`, Tailwind `@theme` mapping in `globals.css`.
- Unit tests for `money.ts` (Persian digits, thousand format, rial conversion).
- **Done when:** changing a color in `site.ts` changes the page background; tests pass.

### Phase 3: Layout and menu UI
- Build `Header`, `Footer`, `Button`, `Pill`, `MenuGrid`, `MenuCard` per section 6. `MenuCard` takes props (item, qty, onAdd, onRemove), not the store directly.
- Sold-out state for `available === false`.
- **Done when:** the 4 items render in a 2-column grid at 360px, 390px and 480px with no overflow.

### Phase 4: Cart
- Implement `store.ts` (zustand + persist in sessionStorage, version key `cart-v1`), `selectors.ts`, `QuantityStepper`, `CartPanel`.
- Unit tests for `buildLines` and `getTotal`: empty cart, multiple items, unknown id ignored, unavailable item ignored, no negative quantities.
- Handle SSR/hydration safely so the persisted cart does not cause a hydration mismatch.
- **Done when:** the total updates live, survives a page reload, and tests pass.

### Phase 5: Payment
- Implement `types.ts`, `registry.ts`, `PaymentSection`, `providers/GatewayLink.tsx`, `providers/CardToCard.tsx`, and the `Toast` component.
- Behavior exactly as in section 6. Everything driven by `config/payment.ts` and `content/fa.ts`.
- **Done when:** removing `"gatewayLink"` from `payment.methods` hides that button without touching any component; an empty gateway url shows the toast.

### Phase 6: Polish, QR, static build
- Accessibility pass (labels, focus, contrast, tap targets). Page `<title>` and metadata from `site.name`; favicon.
- `scripts/generate-qr.mjs`: uses the `qrcode` package to write `public/qr/menu.svg` and `public/qr/menu.png` from `NEXT_PUBLIC_SITE_URL`. Add script `pnpm qr`.
- Write a short `README.md`: run, build, deploy, "how to change things" table (section 8), how to generate the QR.
- **Done when:** `pnpm build` outputs a working `out/` folder; opening it from a static server works; `pnpm qr` writes the QR files.

## 8. "How do I change X?" cheat sheet (put in README)

| I want to change | Edit only |
|---|---|
| Cafe name, taglines, footer text | `src/config/site.ts` |
| Colors | `site.theme` in `src/config/site.ts` |
| Add, remove or reprice an item | `src/config/menu.ts` |
| Mark an item as sold out | `available: false` in `menu.ts` |
| Add item photos | drop file in `public/images/menu/`, set `image` in `menu.ts` |
| Gateway link | `payment.gatewayLink.url` |
| Card number | `payment.cardToCard.cardNumber` |
| Hide or reorder payment methods | `payment.methods` |
| Any button label, message or aria text | `src/content/fa.ts` |
| Add a new payment method | new file in `features/payment/providers/`, one entry in `registry.ts`, id in `types.ts` and `payment.methods` |

## 10. Deployment

- `pnpm build` creates the static site in `out/`. Upload its contents to the host root or a subfolder (for a subfolder set `NEXT_PUBLIC_BASE_PATH=/menu` before building).
- Use a **stable URL** (for example a subdomain like `menu.yourdomain.ir`). The printed QR points to it. If the URL changes, every printed QR is dead, so decide the final domain before printing.
- Set `NEXT_PUBLIC_SITE_URL` to that URL, then run `pnpm qr` and use the generated SVG on the poster.

## 11. Known limitations (v1)

- No payment verification. The page cannot know whether a customer really paid. The seller confirms payments manually (bank SMS or receipt).
- The amount is not pre-filled in the gateway, unless the gateway supports an amount parameter in its link. If it does, extend `GatewayLink.tsx` to build the url from the total.
- Static export means no API routes. Real gateway integration with verification (callback and verify call) needs a server. Plan for it by keeping everything behind the payment provider interface; the switch is removing `output: "export"` and adding route handlers.

## 12. Roadmap (NOT part of v1)

2. Categories and tabs (`category` field already reserved).
3. Optional order note and an "Send order to Telegram/Bale/WhatsApp" button.

5. PWA with offline cache (useful where mobile signal is weak).
